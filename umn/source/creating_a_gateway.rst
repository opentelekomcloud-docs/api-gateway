Creating a Gateway
==================

Before using API Gateway, you need to create a gateway. A gateway is an independent resource space. All operations are performed within a gateway, and resources in different gateways are isolated from each other.

Constraints
-----------

-  Permissions

   -  You must be assigned both the **APIG Administrator** and **VPC Administrator** roles so that you can create gateways.
   -  Alternatively, you must be attached the **APIG FullAccess** policy.
   -  You can also be granted permissions using custom policies. For details, see :ref:`Custom APIG Policies <apig_03_0050__section045282915216>`.

-  Gateway

   -  By default, one account can create up to five gateways in a project. To create more dedicated gateways, contact technical support to increase the quota.

-  Network

   -  Subnet planning: If you use **192.x.x.x** or **10.x.x.x**, APIG uses **172.31.32.0/19** as the internal subnet. If you use **172.x.x.x**, APIG uses **192.168.32.0/19** as the internal subnet.
   -  Private IP addresses in a subnet: The basic, professional, enterprise, and platinum editions of APIG require 3, 5, 6, and 7 private IP addresses, respectively. Check whether the subnet you choose has sufficient private IP addresses on the VPC console.
   -  VPC: After a gateway is created, the VPC cannot be changed.
   -  Security group: After you purchase a gateway, the security group does not take effect. To disable some IP addresses, use :ref:`access control policies <apig_03_0027>`.

Preparing the Network Environment
---------------------------------

-  You are advised to deploy your gateways in the same VPC as your other services to facilitate network configuration and secure network access. Resources (such as ECSs) in the same VPC can use the private IP addresses of the gateways to call APIs.

-  Similar to a firewall, a security group controls access to a gateway through a specific port and transmission of communication data from the gateway to a specific destination address. For security purposes, create inbound rules for the security group to allow access only on specific ports.

   The security group bound to a gateway must meet the following requirements:

   -  Inbound access: Enable the **1026** (TCP) port of the VPC CIDR block associated with the gateway.
   -  Inbound access: To allow the APIs in the gateway to be accessed over public networks or from other security groups, configure inbound rules for the security group to allow access on ports **80** (HTTP), **443** (HTTPS), and **1026**.
   -  Outbound access: If the backend service of an API is deployed on a public network or in another security group, add outbound rules for the security group to allow access to the backend service address through the API calling port.
   -  If the frontend and backend services of an API are bound with the same security group and VPC as the gateway, no inbound or outbound rules are needed to allow access through the preceding ports.

------------------

#. In the navigation pane, choose **Gateways**.

4. Click **Create Now**.
5. Confirm the gateway configurations. The gateway is created with the status displayed on the screen.

   -  Return to the gateway list and check the status of the created gateway. If the status is **Running**, the gateway has been created.
   -  For details about how to view or edit a gateway, see :ref:`Viewing or Modifying Gateway Information <apig_03_0038>`.
   -  Before deleting a gateway, ensure that the deletion will not impact your services.
